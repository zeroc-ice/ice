# Ice: threat model for the OSS Scanner

Ice is an RPC framework that implements its own binary protocol (the Ice protocol) over various transport protocols
(TCP, WebSocket, Bluetooth RFCOMM, and more) with or without TLS.

Ice also includes an IDL (Slice) used to describe RPCs, and Slice compilers that generate code from Slice definitions.

Ice provides runtimes and dev-kits for several languages (C++, C#, Java, JavaScript, MATLAB, Python, PHP, Ruby, and
Swift). It also provides a set of services implemented in C++: Glacier2, IceGrid, IceStorm, IceBridge; client
libraries for Glacier2, IceGrid, and IceStorm are available in all languages except MATLAB.

DataStorm, a pub/sub library, is C++ only. The IceBox server is available in C++, C#, and Java.
The IceDiscovery and IceLocatorDiscovery plug-in libraries are available in C++, C#, and Java.

The MATLAB, Python, PHP, Ruby, and Swift runtimes are built on the C++ runtime.

`SECURITY.md` lists the supported versions. This scan targets `main`; fixes are cherry-picked to the 3.8 release
branch.

## Where untrusted input enters

The attacker is a remote peer that can open a connection to, or send datagrams to, an Ice endpoint, over any
transport: TLS authenticates the peer only when the server requires and verifies a client certificate, and a
malicious peer can hold a valid one. On a plain (non-TLS) connection, the attacker can also sit on the network path.

In order of exposure:

- **The Ice protocol**, in every runtime: message headers, framing and bzip2-compressed messages. In C++:
  `cpp/src/Ice/Protocol.cpp` and `ConnectionI.cpp`; the equivalents live under `csharp/src/Ice`,
  `java/src/com.zeroc.ice` and `js/packages/ice/src/Ice`. `Ice.MessageSizeMax` (1 MB by default) bounds the size of the
  messages a peer may send.
- **The Ice encoding**, in every runtime: the unmarshaling of request and reply bodies through the unmarshaling code
  generated by the Slice compilers. The most intricate parts, and the most likely to hide bugs, are optional fields,
  classes and class graphs, exceptions, and proxies with the endpoints they carry. In C++:
  `cpp/src/Ice/InputStream.cpp`; the equivalents live under `csharp/src/Ice`, `java/src/com.zeroc.ice`,
  `js/packages/ice/src/Ice`, `swift/src/Ice` and `matlab/lib/+Ice`. Python, Ruby and PHP unmarshal with the type
  descriptors generated by the Slice compilers, interpreted in C++ by `python/modules/IcePy/Types.cpp`,
  `ruby/src/IceRuby/Types.cpp` and `php/src/Types.cpp`. `Ice.ClassGraphDepthMax` (10 by default) bounds the depth of the
  class graphs a peer may send, and in C++ and Swift the unmarshaling rejects a class graph with a cycle unless
  `Ice.AcceptClassCycles` is on (it is off by default).
- **Transports**: TCP, UDP (including multicast), WebSocket (`WSTransceiver`, `HttpParser`, `Base64`, `SHA1`), SSL/TLS
  (`cpp/src/Ice/SSL`: OpenSSL on Linux; certificate verification and the `IceSSL.TrustOnly` and distinguished-name
  parsing in `RFC2253.cpp`), and Bluetooth (`cpp/src/IceBT`).
- **Glacier2**, the router meant to be exposed to the Internet: session creation, the permissions verifiers, request
  forwarding and buffering, the filters that restrict what a client may reach, and anything a client can do before
  or without a session. A client that escapes its filters or reaches a server it should not is a serious finding.
- **IceBridge**: accepts client connections and opens a separate connection to the target for each of them. It relays
  each request's payload without unmarshaling it, but it processes each request's protocol fields, queues requests until
  the outgoing connection is established, and implements the `Router` and `RouterFinder` interfaces.
- **IceGrid registry and nodes**: the client-facing locator and query interfaces, session and admin session creation,
  replica and node sessions between registries and nodes.
- **IceStorm and DataStorm**: publishers and subscribers send data and control messages to the service or to each
  other. DataStorm nodes also accept multicast discovery messages by default (`DataStorm.Node.Multicast.Enabled`).
- **IceDiscovery and IceLocatorDiscovery**, in C++, C# and Java: multicast requests and replies from anyone on the
  local network.

## What is trusted

- **Configuration**: properties, configuration files, command-line arguments and environment variables. They are
  chosen by the operator.
- **Slice definitions and the Slice compilers**: `.ice` files are written by the application developer and compiled at
  build time. Compiler crashes on malformed Slice are ordinary bugs, not vulnerabilities. The generated code is not
  trusted, however: it unmarshals peer data at run time.
- **The application's own code**: servants, custom verifiers, Slice loaders, dispatch middleware.
- **Authenticated administrators**: an IceGrid administrator can deploy and start arbitrary servers, and Ice admin
  facets (`Ice.Admin`) can change properties and shut down the process. These are code-execution or full-control
  privileges by design; something only reachable with them is not a vulnerability unless a less privileged party can
  reach it.
- **Local files and the local machine**: IceGrid and IceStorm databases (LMDB), certificates and key stores on disk,
  log files.

## How to exercise it

The image has two builds, described at the top of `/src/.oss-scanner/Dockerfile`:

- `/src`: every buildable language mapping, debug build with asserts enabled. Each language directory has an
  `allTests.py`; run one test with, for example, `python3 /src/cpp/allTests.py --filter=Ice/stream`, or a whole
  mapping with `--workers=<count>`, which runs tests in parallel, each worker on its own port range. Without a
  network, tests that use multicast (`Ice/udp`, IceDiscovery) or listen on all interfaces (`-h *`, for example
  `Ice/exceptions` and `IceSSL/configuration`) fail during setup; those failures are environmental, not findings.
- `/opt/ice-asan`: C++ only, with AddressSanitizer and UndefinedBehaviorSanitizer. Use it to confirm memory-safety
  findings: `python3 /opt/ice-asan/cpp/allTests.py --filter=Ice/stream`. To rebuild it after a change, pass the
  sanitizer flags the Dockerfile uses, or the link fails:
  `make -C /opt/ice-asan/cpp CXXFLAGS="-fsanitize=address,undefined -fno-sanitize=vptr -fno-omit-frame-pointer -O1"
  LDFLAGS="-fsanitize=address,undefined -fno-sanitize=vptr" srcs tests`.

The tests under `cpp/test` (and `csharp/test`, `java/test`, ...) are the best examples of how to stand up a
server and client. A reproducer that sends raw bytes over a socket to a test server is the most convincing form for an
unmarshaling bug.

## How we rate severity

Rate by what a remote peer can do under the attacker model above:

- **Critical**: remote code execution; memory corruption (out-of-bounds write, use-after-free, double free); an
  out-of-bounds read whose content reaches the attacker; a Glacier2 filter or session bypass; TLS certificate
  verification that accepts a certificate it should reject.
- **High**: a crash of any Ice process, in any language, triggered by a crafted message, including an out-of-bounds
  read that only crashes.
- **Medium**: resource exhaustion that small input can cause and that `Ice.MessageSizeMax` and the other configured
  limits do not bound.
- **Low**: denial of service that needs a large amount of traffic or a misconfigured limit; problems confined to the
  connection or request the attacker sent; information disclosure into the server's own logs.

An exception sent back to the peer for malformed input (`MarshalException`, `ProtocolException`, closing the
connection) is the expected behavior, not a finding.

A missing validation is rated by what it lets a peer do, shown with a reproducer, in the sanitizer build when memory
safety is in question; a check whose absence only changes which exception the peer gets is not a finding. The image
is a debug build: an assertion failure shows that a check is missing, but the rating depends on what a release build
does without it.

## Already considered and not vulnerabilities

- Full exception detail in logs at opt-in trace levels (for example `Glacier2.Trace.Session`, `IceGrid.Trace.*`).
  Tracing is off by default, the detail stays in the server's log, and clients only get a generic error.
- The plain transports (`tcp`, `udp`, `ws`, `bt`) are unauthenticated and unencrypted by design. The secure variants
  (`ssl`, `wss`, `bts`) are the answer; adding authentication to the plain ones is not.
- Memory or CPU proportional to the size of a message, which `Ice.MessageSizeMax` bounds (for a compressed message,
  the uncompressed size is checked against the limit before anything is allocated). Memory or CPU out of proportion
  to the message size, such as an allocation sized by a count that is not checked against the bytes remaining in the
  message, is a bug.
- Certificate revocation checking is off by default (`IceSSL.RevocationCheck=0`, and cache-only when enabled). Many
  deployments use private CAs without OCSP or CRL distribution points.
- Problems that need `Ice.AcceptClassCycles=1`. With cycles accepted, the application owns the lifetime of the cyclic
  class graphs it receives; turning the default rejection off is a documented choice the application makes.
- A UDP server replies to the source address of the last datagram it received, so a spoofed datagram can redirect
  replies. UDP is documented as an insecure transport.
- Glacier2 forwards the client's request context to the permissions verifiers on purpose. The reserved `_con.*`
  connection keys are removed first.
- The parsers of the `icegridadmin` and `icestormadmin` command-line tools read input from a trusted local operator.
- Cleanup that is skipped only when a fatal exception (for example `std::bad_alloc`) escapes.
- Races at the idle-timeout boundary of a connection. A connection only reaches that boundary after receiving nothing,
  not even a heartbeat, for a full idle timeout; the outcome is a closed connection that the client re-establishes.
- A DataStorm partial update that has no base value (never set, or removed) is discarded with a warning, by design.
- Hardening that only matters after an API contract is already violated by the application itself.

## Reports and patches

- Name the language mapping and the component in the title, and say whether the bug also applies to the 3.8 branch.
- When the same unmarshaling logic exists in several mappings (C++, C#, Java, JavaScript, Swift), check the others and
  report each affected mapping in the same report.
- Patches must keep the wire format and the public API unchanged unless the report explains why that is impossible.
